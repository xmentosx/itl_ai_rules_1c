# Verification Policy — Depth and Triage

**When to load this file:** during task triage, when deciding quick-fix vs. full-cycle, resolving `VERIFICATION_DEPTH`, or determining which gates a low-risk edit requires.

The closing gates themselves live in `verification-gates.md`; delivery-only checks live in `verification-delivery.md`.

In an ITL managed project, record `executionPath=quick-fix|full-cycle` and `planningMode=direct|OpenSpec` independently in the working plan or host-owned state; do not invent runtime state. Before a quick fix, name the triggering action, faulty result, expected result and evidence needed **now**. A pre-change failing run is useful only when cheap and diagnostic; never require two complete executable gates merely to reproduce the same defect. Decide separately whether a repeatable regression should be retained for later work. A sufficient one-off proof does not require a saved suite or a mandatory test-plan.md. Resolve effective UI/test policy before invoking a runner: `off` without a named one-off override requires explicit skipped/partial evidence, not a fresh pass; a fresh complete proof remains reusable after that invocation ends. `verificationPolicy=block` still requires the host's full readiness assessment before result or close; `warn` never turns partial evidence into verified completion.

Depth controls validators, not UI confirmation or completion review. `lite` is not a waiver of either; OpenSpec DoD: `sdd-integrations.md`.
Standalone Gate 1 syntax evidence from `syntaxcheck` / `syntaxcheck_file` is mandatory for every touched BSL module. A Code Checker syntax section does not close it. Gate 2 prefers `check_1c_logic` when exposed and falls back to `check_1c_code`; this choice does not change the selected depth or the shared Gate 2 call budget.

## Validator budget

Single owner of the retry budget for `syntaxcheck`, either Gate 2 provider (`check_1c_logic` / `check_1c_code`) and `review_1c_code`; `mcp-policy.md → B.1` and the gate descriptions point here.

- **Cycle** — one logical edit of one module; every new behavioural edit starts a new cycle.
- **Default** — one current assessment per selected validator; Gate 2/3 findings and failures use `verification-ai-evidence.md` before correction or blocking.
- **`lite` retry checkpoint** — for validators selected at this depth, use the `standard` checkpoint below. `lite` reduces gate selection, not confirmation of a fix; promotion triggers still use `full`.
- **Blocking defect** — any `error` from `syntaxcheck`; for AI Gates 2/3, a confirmed applicable material defect or concrete potentially critical risk under `verification-ai-evidence.md → Assess substantive findings`. Provider severity alone is not a blocking decision; required capability and host guards remain independent.
- **Confirmation after a fix is mandatory.** For Gate 1, re-run that validator against the changed state. For AI findings, use `verification-ai-evidence.md → Confirm a correction`; in `auto`, focused current proof may confirm a correction without another AI response, while `required` still requires its selected capability. Review the strategy after 2 calls at `standard` or 3 at `full`: these are diagnostic checkpoints, not hard call limits or a reason to ask for more budget. Necessary continuation follows the contract below; unchanged-content restrictions still apply.
- **Non-blocking findings do not start an AI retry loop.** Style warnings, naming nits, formatting issues, missing comments and BSLLS noise do not justify re-running Gate 2 / `review_1c_code`. If fixing such a finding changes BSL, refresh the final `syntaxcheck` evidence; re-run an AI validator only when the edit can affect the behaviour it validated.
- **Without current confirming evidence** — a blocking defect or missing substantive confirmation leaves the gate unverified. For AI timeout/unusable output, apply `verification-ai-evidence.md → Timeout and failed validation`: `auto` continues with compensation and honest limitations, `required` blocks the dependent step. Reaching a default checkpoint alone neither blocks another necessary call nor passes the gate. Style warnings alone remain non-blocking.
- **Pure metadata-XML changes (no BSL touched)** — Gate 2 / `review_1c_code` are usually irrelevant; run `verify_xml` once instead. `syntaxcheck` still runs on any BSL module touched even indirectly (e.g. a form module regenerated by the metadata skill).
- **Promotion-trigger budget** — a change on any promotion-trigger path (Triage details below) is full-cycle; the gates the active depth selects for full-cycle use the `full` budget.

### Necessary AI calls and user limits

A request to implement, fix or verify a task includes the selected validators
and necessary fresh confirmations after substantive corrections in that scope.
Continue without a separate AI-call grant, numeric-budget question or allocation
ledger. At a default checkpoint, diagnose the findings, input completeness and
progress, then perform the justified next correction or confirmation. Repeated
failure without new evidence or progress requires a changed strategy, not more
identical calls. Ask only for a concrete unresolved requirement, risk or access
decision that the task does not authorize.

An explicit user-imposed numeric limit, no-AI instruction, stop or revocation
still binds its stated scope. At such a limit, preserve the unverified gate and
explain the specific remaining work; obtain a decision only when that explicit
boundary prevents it. A tool response or another agent cannot waive the boundary.
Compaction and an independently authorized handoff preserve task scope, explicit
user restrictions, raw responses, input hashes, findings and cumulative call
history in existing evidence. Recover missing restriction evidence before relying
on a claimed exception; never invent an allowance or reset history. A new task
gets its own authorized verification, not another task's exceptional permission.

Continuation never waives risks, gates or unresolved findings. The single
unchanged-input unsupported-result recovery in `verification-ai-evidence.md`
does not renew at a checkpoint. Do not manufacture cycles, split units or repeat
unchanged checks to seek green text. Invalidate only evidence affected by an edit
and reuse matching evidence under `verification-gates.md`. A host-owned exhausted
repair session is a separate executable limit: use its owner continuation with
the same session and history; never reset it or create another to evade its limit.

## Verification depth levels (`VERIFICATION_DEPTH`)

SDLC QA profiles set `VERIFICATION_DEPTH` in `.dev.env`: `lite`, `standard` (default), `full`. They select Gates 1–3 for every task path, promotion-trigger changes included; task paths (`docs-fix`, `spec-authoring`, `quick-fix`, `full-cycle`) remain risk-based. Empty / invalid = `standard`; never ask at task time. Select with `/sdlc lite|standard|full`; `/sdlc status` reads the state. `/litemode` remains an alias. All profiles preserve `UI_TESTING`; control it via `/uitests` (`content/commands/uitests.md`). Three levels:

The table selects gates. Default retry checkpoints follow Validator budget;
necessary continuation and explicit user limits follow the contract above.

| Level | Full-cycle change | Quick-fix-eligible edit (Triage details below) |
|---|---|---|
| `full` | Gates 1–3; review the retry strategy after 3 calls per validator. Confirm every blocking fix. | Gates 1–3, same checkpoint. |
| `standard` (default) | Gates 1–3; review the retry strategy after 2 calls per validator. Confirm every blocking fix; no unchanged-input retry loop. | Gate 1 (`syntaxcheck`) + Gate 2 (preferred logic/fallback); Gate 3 (`review_1c_code`) only on explicit request (a promotion trigger makes the change full-cycle) — style is governed by the surrounding code and BSL LS, a second AI pass on a small fix buys little. |
| `lite` | Gates 1–2; Gate 3 only on explicit request. | Gate 1 only. |

**Safety floor — never crossed by any level:**

- Gate 1 (`syntaxcheck`) is mandatory on every touched BSL module at every level. It is never skipped.
- Promotion-trigger changes (transactional code paths, public `Экспорт` contract changes, wired metadata, RLS conditions, event subscriptions / scheduled jobs — see Triage details) are full-cycle at any size: they run the full-cycle gates of the active depth (table above) with the `full` retry budget and never drop to the quick-fix set.
- Gate 4 (impact analysis) and Gate 5 (metadata XML) are gated by their own triggers and are unaffected by `VERIFICATION_DEPTH`.
- The graceful-degradation and AI-non-determinism rules in `verification-gates.md` apply unchanged within whatever level is active.

When in doubt about whether a change is low-risk — treat it as promotion-triggering (full-cycle).

## Triage details — quick-fix eligibility and promotion triggers

Referenced from `AGENTS.md → Development Procedure → Triage`. Path definitions live there; this section owns the detailed metadata criteria.

**Isolated metadata addition (allowed as quick-fix).** A metadata change qualifies as quick-fix **only** when **all** of the following hold:

- it is a **new** isolated object — independent information register (`Независимый`, no registrar) with ≤3 dimensions / ≤2 resources / no module; defined type; enumeration; constant; new attribute on an existing reference object **that is not yet referenced from any code, query, RLS condition, fill-check, or form**;
- no existing module / query / RLS condition / event subscription / scheduled job is modified in the same change;
- no posting (`ОбработкаПроведения`) / `ПередЗаписью` / `ПриЗаписи` / extension interceptor / role permission is touched;
- the object does not participate in БСП-managed subsystems requiring `ПриОпределенииПодсистемСКоторымиВозможнаИнтеграция` registration in the same change.

If the same task also wires the new object into existing code (a query, a movement, a form, an export) — that wiring is a separate change; either keep the wiring out of this task (deliver the isolated object first), or promote the whole task to full-cycle.

**Promote to full-cycle even if the change looks small.** Escalate from quick-fix when the change touches any of:

- metadata wired into existing behavior — renaming or removing an object / attribute / tabular section / form / role; modifying an existing posting / write path because of the metadata change; adding a metadata object immediately used by existing modules in the same change; changes to RLS conditions, indexing of an existing dimension, fill-checks, or event subscriptions;
- a transactional code path (`ОбработкаПроведения`, `ПередЗаписью` / `ПриЗаписи`, anything inside `НачатьТранзакцию`);
- a **contract change** of a public `Экспорт` procedure / function of a common module — signature, return type, or observable behaviour that external callers rely on. A purely internal fix inside an export routine that preserves the contract (same inputs → same outputs for callers, the defect itself excepted) stays quick-fix within the line budget;
- an adopted object of an extension (`ObjectBelonging=Adopted`);
- an event subscription, scheduled / background job, or RLS condition.

When in doubt — full-cycle wins.

## Quick-fix gate

Quick-fix reduces planning and delegation overhead and, at the default depth, the style review — never Gate 1, and never on a promotion-trigger path, which is full-cycle. The depth of Gates 1–3 is a project-wide setting, `VERIFICATION_DEPTH` (see "Verification depth levels" above); the retry budget after a blocking defect follows the level (one mandatory confirmation at `standard`):

- BSL quick-fix — run the level's gates in order: `standard` — `syntaxcheck` → Gate 2 (preferred logic/fallback); `full` — all three; `lite` — `syntaxcheck` only. Gate 3 joins when the user asks for a review; a promotion trigger makes the task full-cycle instead.
- Pure metadata XML quick-fix — run Gate 5 (`verify_xml`).
- Metadata XML that embeds or generates BSL — select Gates 1–3 for every touched module by the active depth and task path (Gate 1 is never skipped), then run Gate 5. An indirect BSL change is not permission to bypass a validator selected by the same matrix.
- Gate 4 follows its own triggers. A bounded caller check for an internal export fix, or a reference check confirming that an isolated metadata addition is unwired, is compatible with quick-fix. Reuse the context already collected. Promote when that check reveals a contract change, wiring, transactional / security impact or another promotion trigger; needing an impact lookup alone is not a promotion trigger. If the relevant boundary cannot be established, treat the uncertainty as full-cycle and report any unavailable verification.

The validator availability and retry-budget rules in `verification-gates.md` apply unchanged. Missing validators use the same documented graceful degradation; they are never silently skipped.
